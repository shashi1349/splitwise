# Deployment guide

This document is the runbook for putting Splitwise-Lite on the public
internet. The repo ships with everything required (Dockerfiles, blueprint
configs); the steps below are the ones a human still needs to drive.

> **Honest note:** the Kiro session that built this project doesn't have
> Render or Vercel credentials, so the README's "live demo" links are
> placeholders. Once you finish the steps below, swap them in and the
> rest of the docs will be accurate.

---

## 1 — Local stack (no signup needed)

```bash
git clone https://github.com/shashi1349/splitwise.git
cd splitwise
docker compose up --build
```

After the build:

| Service  | URL                                          |
| -------- | -------------------------------------------- |
| Frontend | <http://localhost:5173>                      |
| Backend  | <http://localhost:8080>                      |
| Swagger  | <http://localhost:8080/swagger-ui.html>      |
| Health   | <http://localhost:8080/actuator/health>      |
| Postgres | `postgres://splitwise:splitwise@localhost:5432/splitwise` |

Stop with `docker compose down` (or `down -v` to wipe the database).

## 2 — Backend on Render (Docker + managed Postgres)

> **Heads-up before you click anything.** Render's free PostgreSQL
> only exposes an *external* endpoint. The blueprint at the repo root
> deliberately leaves the three JDBC env vars as `sync: false` so you
> can fill them in from the External Database URL after the DB is
> provisioned. Skipping this is the most common reason a first deploy
> crashes with `UnknownHostException: dpg-xxxxx-a` — see §6 for the
> exact symptom and fix.

### 2.1 — Create the blueprint

1. Push this repo to GitHub.
2. Render dashboard → **New → Blueprint** → pick the repo.
   `render.yaml` provisions:
   - a free PostgreSQL instance named `splitwise-db`
   - a free web service named `splitwise-api` (builds `backend/Dockerfile`)
3. The first build will start, but the **first deploy will fail**
   because the three database env vars are intentionally blank. That's
   expected — finish step 2.2 to fix it.

### 2.2 — Wire the database into the web service

1. Render → **splitwise-db** → **Info** tab. **Don't parse the URL** —
   Render shows the four fields you need explicitly. Note them down:

   | Render field   | What it is                                              |
   | -------------- | ------------------------------------------------------- |
   | **Hostname**   | external host, ends in `.<region>-postgres.render.com`  |
   | **Port**       | `5432`                                                  |
   | **Database**   | actual db name (often has a random suffix — copy verbatim) |
   | **Username**   | actual db user (often has a random suffix too)          |
   | **Password**   | click the eye icon to reveal                            |

   Render reserves the right to append suffixes to `databaseName` and
   `user` from `render.yaml` to avoid name collisions; in particular,
   after you click **Reset** on the database the new name almost always
   has a suffix. The values shown on this tab are authoritative.

2. Render → **splitwise-api** → **Environment** tab. Set:

   | Key                          | Value                                                                                                |
   | ---------------------------- | ---------------------------------------------------------------------------------------------------- |
   | `SPRING_DATASOURCE_URL`      | `jdbc:postgresql://<Hostname>:<Port>/<Database>?sslmode=require`                                     |
   | `SPRING_DATASOURCE_USERNAME` | exact value from **Username** above                                                                  |
   | `SPRING_DATASOURCE_PASSWORD` | exact value from **Password** above                                                                  |

   Concrete example:

   ```
   SPRING_DATASOURCE_URL = jdbc:postgresql://dpg-XXXXXXXX-a.oregon-postgres.render.com:5432/splitwise_abc1?sslmode=require
   ```

   The `?sslmode=require` part matters: Render's Postgres demands TLS
   even on the external endpoint, so the JDBC driver must negotiate it.
3. **Save Changes** — Render redeploys automatically. Tail the logs;
   you should see `Started SplitwiseApplication in N seconds`,
   followed by `Tomcat started on port 10000`.
4. Smoke-test:
   ```bash
   curl https://splitwise-api.onrender.com/actuator/health
   # {"status":"UP"}
   ```

### 2.3 — CORS

Set `APP_FRONTEND_ORIGIN` to your future Vercel URL
(e.g. `https://splitwise-lite.vercel.app`). Save → redeploy.

`JWT_SECRET` is auto-generated by Render and never returned to the
caller. Rotating it forces all existing tokens to fail signature
verification — desired behaviour for a security event.

### 2.4 — If you upgrade Postgres to a paid plan

Internal networking becomes available. Edit `render.yaml`:
swap the three `sync: false` entries for the commented `fromDatabase`
block at the bottom of the file, then push. The web service will
auto-pull host/port/db/user/password from the DB resource and you no
longer need to paste the External URL anywhere.

## 3 — Frontend on Vercel

1. Vercel → **Add New → Project**, import the same GitHub repo.
2. **Root directory:** `frontend`. Vercel auto-detects Vite (and
   `frontend/vercel.json` makes the SPA fallback explicit).
3. **Environment Variables:**
   - `VITE_API_BASE_URL` = the Render URL from step 2.2
     (e.g. `https://splitwise-api.onrender.com`)
4. Deploy. Vercel will give you `https://<project>.vercel.app`.
5. Go back to Render, set `APP_FRONTEND_ORIGIN` to that Vercel URL,
   and redeploy the backend so CORS allows the new origin.

## 4 — Smoke-test the deployed stack

```bash
APP=https://splitwise-api.onrender.com

# Register
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","displayName":"Alice","password":"alicepass1"}' \
  $APP/auth/register

# Login
TOKEN=$(curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"alicepass1"}' \
  $APP/auth/login | jq -r .token)

# Authenticated call
curl -s -H "Authorization: Bearer $TOKEN" $APP/groups
```

Then open the Vercel URL in a browser, register/login, create a group,
add a member, add an expense, and confirm the Balances and Settle Up
tabs show what you expect.

## 5 — Rotating secrets / wiping data

| Action            | How                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Rotate JWT secret | Render → service env vars → regenerate `JWT_SECRET` → redeploy. All existing tokens become invalid.                                  |
| Reset DB          | Render → database → **Reset** (wipes data, keeps schema migrations on next boot).                                                    |
| Bump CORS origin  | Update `APP_FRONTEND_ORIGIN` and redeploy backend.                                                                                   |
| DB password change| Edit `SPRING_DATASOURCE_PASSWORD` on the web service to match. (Render doesn't auto-rotate the manual env var.)                      |

## 6 — Troubleshooting

### `UnknownHostException: dpg-xxxxx-a`

You're using the *internal* short hostname against a *free* Postgres.
Free Postgres doesn't expose its internal network to free web services.
Fix: paste the **External** Database URL into `SPRING_DATASOURCE_URL`
(see §2.2). The hostname must be the long form ending in
`.<region>-postgres.render.com`.

### `password authentication failed for user "splitwise"`

The password you pasted into `SPRING_DATASOURCE_PASSWORD` doesn't match
the DB *or* the username doesn't match what Render actually created
(Render often appends a suffix). Re-copy both **Username** and
**Password** from the splitwise-db Info tab. They get rotated whenever
you click **Reset** on the database.

### `FATAL: database "splitwise" does not exist`

You connected successfully but the database name in the JDBC URL path
is wrong. Open splitwise-db Info, look at the **Database** field
explicitly (do not parse the External URL — copy from the field), and
put exactly that value after the last `/` in `SPRING_DATASOURCE_URL`.
Render frequently appends a suffix (`splitwise_abc1`) even when
`render.yaml` requested a clean name. As a last resort, create the
missing database manually:

```bash
psql "postgres://<USER>:<PASS>@<HOST>/postgres?sslmode=require" \
  -c 'CREATE DATABASE splitwise;'
```

(Connect to the always-present `postgres` system database, then issue
`CREATE DATABASE`.)

### `No open ports detected, continuing to scan...`

Render's port scan ran before the JVM finished startup. Look earlier in
the log for the *real* failure (typically a Flyway / DB connection
exception). The healthcheck path is `/actuator/health` and the JVM
binds to `${PORT}` automatically — both are correct in the repo.

### Cold-start is slow on free tier

Render free web services sleep after 15 minutes of inactivity. The
first request after a sleep can take 30+ seconds while the container
spins back up. Upgrade to **Starter** ($7/mo) to keep it warm if that
matters.

## 7 — Things I deliberately left out (and why)

- **TLS termination, custom domain.** Render and Vercel both terminate
  TLS for you out of the box; no additional work needed unless you want
  a custom domain. Both providers walk you through that in their UI.
- **Centralised log aggregation.** The CorrelationIdFilter already
  stamps every log line with a request id; pick up the logs from
  Render's log stream into Datadog / Logtail / similar when traffic
  warrants it.
- **Auto-scaling.** Free tier is single-instance. The app is stateless
  (JWT, no sessions) so horizontal scaling is just a slider in the paid
  tier.
